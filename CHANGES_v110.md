# Trothen v110: six real bugs fixed from Joseph's reports, a provider-score fix, a pick-and-drop checkout fix, a store money-safety fix, a country filter, a "Both" pricing fix, six scheduler robustness fixes, and a full audit of the whole app

## 1. Liberia and the US no longer appear mixed together in one provider list
A provider card's own country was missing from the data sent to the browser, so the page had nothing to show except the city — on a listing page with no visible country, pros from different countries could look like they were all in one list even though the real search behind them was already correctly scoped to one country at a time. Fixed by sending the country with each provider, so the card can show it.

## 2. The membership/pricing page no longer gets stuck on the wrong currency
Changing the country dropdown on the pricing page didn't always update the prices shown — sometimes it kept showing the currency from the country you'd left. The page now tracks whether you've actually picked a country yourself versus just loaded the page, so your choice always wins and the dropdown and the prices shown always agree.

## 3. The real root cause of the missing provider score, found and fixed
Joseph reported the provider score not showing on the frontend, and a screenshot of a real, established provider (hundreds of completed jobs) still showing "New on Trothen" confirmed it. The card and the page that display the score were already correct — the real problem was upstream: the daily job that computes and saves every provider's score runs through the whole provider list in one pass, and if even ONE provider's account had a real computation problem, the entire run stopped right there — every provider after that one in the list silently never got a score recomputed that day, with nothing visible anywhere to say so. This is the likely reason an established provider could be stuck showing no score indefinitely. Fixed by giving each provider's own scoring its own try/catch, so one provider's problem is logged and skipped instead of blocking everyone else. Also added a "Recompute now" button for super admins on the Provider Scores page, so scores can be refreshed immediately instead of waiting for the next scheduled run. Verified live: deliberately forced one provider to fail and confirmed every other provider still got a fresh score in the same run.

## 4. "Download My Data" now gives you a real PDF
This used to only offer the raw data file (.json) — asking for a PDF didn't produce one. There is now a real PDF export, built the same way as Trothen's other official documents (contracts, receipts, tax reports), covering your profile, bookings, payouts, disputes and reviews in readable form. The original .json download is still there too, side by side, for anyone who wants the raw file instead.

## 5. Customer service numbers: Dispute, Onboarding, Promotion and General, each separately
Before, there was only one phone number per region — General. Now admins can set a different number for Dispute, Onboarding and Promotion as well, per region, with General as the one that's always there as a fallback when a category hasn't been given its own number. The Dispute help screen now shows the Dispute number specifically, instead of only the General one.

## 6. Ringtone — checked, already working as designed
Joseph reported the ringtone not ringing. Reviewed the real notification-sound code and how it's documented for users: it plays correctly under the conditions it's built for (the tab open, sound not muted by the browser or the phone). No bug was found in the code itself. If this is still happening for Joseph on a specific phone or browser, the next useful piece of information would be which phone/browser and whether the tab was open and unmuted at the time — that would point to a device-specific cause rather than a platform bug.

## 7. Store checkout: no longer a dead end when no pick-and-drop driver is available
A screenshot showed a customer picking "A pick-and-drop driver brings it," being told no driver is available nearby, and the Pay button sitting locked with no clear way forward. The lock itself is correct and stays — you genuinely can't pay for a delivery nobody is available to make. The real gap was that the message gave no direct way out: the customer had to scroll back up and manually reselect pickup themselves. Fixed by adding two buttons right in that message: "Collect it myself instead" (switches straight to pickup and unlocks Pay immediately) and "Check again" (re-checks for a driver without closing the order). Verified live: with zero real drivers available, Pay stays locked and shows both buttons; clicking "Collect it myself instead" unlocks Pay immediately.

## 8. Store: a real, if currently dormant, money-safety bug fixed
Found and fixed an ordering bug in how a store purchase is processed: the system was recording the order and taking the goods off the shelf *before* actually charging the customer, instead of after. Today, with Liberia mobile-money payments still turned off everywhere, the charge step can't fail, so this bug has never actually hurt anyone yet. But the moment Liberia mobile money goes live, a charge that MTN's side rejects would have left a paid-looking order sitting in the system with stock already taken away, for goods nobody had actually paid for. Fixed by charging first, and only ever recording the order or touching stock after the charge succeeds — for both a store purchase itself and a driver's delivery fee for that purchase. Verified live end-to-end (store setup → stock → a real purchase → correct stock reduction → correct order total → correct escrow record) that this fix doesn't change anything about the normal, already-working path.

Beyond that one fix, the rest of the Store feature — goods management, stock holds, pricing in different currencies, delivery by pickup/seller/driver, hand-over photo records, order completion, and receipts — was read through in full and tested live, and found to already be built correctly: money is only ever released once per order, a cancellation after the goods have already changed hands is correctly blocked and routed to a dispute instead of a refund, and a driver's delivery is paid and tracked independently of the seller.

## 9. The same money-safety fix, applied to direct bookings, job-board hires, and additional-payment requests too
After fixing the store-purchase ordering bug above, checked whether the same pattern existed anywhere else — it did, in four more places: booking a specific provider directly, a customer's job posting being matched to a provider, a provider accepting a negotiable price offer, and a customer approving a provider's request for extra payment on a job that turned out bigger than expected. In all four, the booking (or the extra amount) was being written into the system — and in the offer and extra-payment cases, even marked approved and confirmed — *before* the actual charge to the customer was attempted, instead of after. Fixed the same way everywhere: the charge now always happens first, and nothing gets written down, marked matched, or marked active until that charge has actually succeeded. Verified live for all four: a normal direct booking, a normal job-selection hire, a normal negotiable-offer acceptance, and a normal extra-payment approval all still work exactly as before — the only change is the order money changes hands relative to when the paperwork is written.

## 10. "Browse All Pros" — a real country filter
On the full provider directory page ("Browse All Pros"), pros from different countries could show up together in one list with no way to pick just one country — the same kind of mixing item 1 fixed on the homepage, but on a page that's deliberately meant to show every provider, so it needed a different fix: a real filter, not a scope. There's now a country dropdown on that page, right next to the category filter and the sort dropdown, listing only the countries that actually have a pro on the platform. It works together with the category filter (e.g. "Plumbing" + "Liberia" at once), and the count at the top always says plainly which category and country you're looking at.

## 11. GPS and location: checked, already working correctly
At Walter's request, went through every part of the app that uses real GPS location — the distance math itself, sharing your location as a provider or a customer, live location while a pro is en route to a job, the pick-up/drop-off photo records with their own location and route trail, and the radius a provider is willing to travel for a job. All of it was found to already be built correctly: the distance calculation is accurate, bad or fake coordinates (like 0,0, the "middle of the ocean" GPS has when it fails) are correctly rejected everywhere this data comes in, and a provider who hasn't shared their location or set a travel radius is never silently hidden from search — only ever filtered out when there's a real distance to compare against. No bugs found, no changes made.

## 12. A full pass over every money-moving screen, one more real fix found
Following "fix everything and best practice," went through the entire payments file line by line — payment methods, payout requests, payment history and PDF statements, the escrow summary, and the admin financial reports — plus membership subscribe/cancel and the identity-verification webhook. One more real instance of item 9's bug was found: when a customer approves a provider's request for extra payment on a job, that approval is a separate flow from the original booking and had the same gap — the extra amount was being marked approved and added to the job's total before the charge for it was actually attempted. Fixed the same way: the charge is attempted first, and the approval is only recorded once it succeeds. Verified live: a normal approval still correctly raises a $50 job to $75 with the extra $25 added to escrow.

Everything else gone through this round was found already correctly built, with no changes needed: payout requests (including the safeguards against two payout requests firing on the same provider at once), payment history and PDF statements, the escrow summary, admin financial-by-region reporting, membership subscribe/cancel, the identity-verification webhook, and dispute resolution (refund / release / split) — including its existing protection against releasing or refunding the same disputed job twice.

## 13. "Both" pricing — a real option a provider could never actually save
Settings already has a full "Both" choice next to "Hourly Rate" and "Mutual Agreement" (a customer can either book at the provider's hourly rate or make their own offer, provider's choice which to accept), and the booking logic in the backend already understands it. But saving it was broken on both ends: the server rejected "both" outright as an invalid pricing model, and even if it hadn't, the page never sent the hourly rate along with it (it only did that for plain "Hourly Rate"). The practical effect: any provider who picked "Both" and clicked Save got an error, or, had the server not rejected it, would have had their rate silently left unset. Fixed both sides — the server now accepts "both", and the page now sends the hourly rate for it too. Verified live: PATCHing a real account to pricingModel "both" with a $42 rate now succeeds and the rate is saved correctly.

## 14. One more robustness fix, found while checking the other scheduled sweeps
After finding and fixing the provider-score sweep's "one bad record blocks everyone after it" bug last round, checked every other daily/scheduled sweep in the app for the same shape of problem. Found it in six more: the exchange-rate refresh, the unverified-account reminder, the ID-document retention cleanup, the exact-location retention cleanup, the payout settlement sweep, and the monthly top-scorer award. None of these had caused a known, reported problem yet, but all six had the same structural risk: one bad record partway through could silently stop every record after it in that day's run from being handled. Fixed the same way as the provider-score sweep: each item in each sweep now has its own try/catch, so one failure is logged and skipped instead of stopping the rest. Also fixed a smaller, related issue in the unverified-account reminder: it was marking a person as "reminded" before actually sending the reminder, so a failed send would have permanently stopped them from ever getting a real one — it now sends first, then marks.

Also went through every route file not yet looked at this engagement — business tools (quotes, invoices, expenses, tools, tax reports), portfolio and job photos, and the rest of auth (signup, login, Google sign-in, two-factor, password reset, phone verification, account closure) and the rest of the store feature (goods management, extra skills, admin review/approval) — and found them already correctly built, no changes needed.

## 15. Found the real reason Joseph's card still shows "New on Trothen" after recomputing
This is not the same bug as item 3 — item 3 is fixed and confirmed working. This is a separate, genuine finding: a Trothen Score only ever counts bookings actually completed **through Trothen** — it has no way to know about work a pro did before joining, or off the platform. A pro's "315 jobs" / "4.9★" shown on their card is their own profile figure; the score needs 5 bookings completed *on Trothen itself* before it stops being provisional, and nothing — including "Recompute now" — can substitute real completed-on-Trothen bookings for that. Reproduced this exactly: a test account with a high profile "jobs" number but zero completed Trothen contracts gets a real computed score (72) that stays marked provisional (`isNew: true, completedJobs: 0, jobsUntilScored: 5`) no matter how many times it's recomputed — which is the system working as intended, just not visible anywhere an admin could see it.

The real gap: the admin "Breakdown" view (Admin → Provider Scores → Breakdown) already had this exact information available from the server the whole time (`isNew`, `completedJobs`, `jobsUntilScored`) but never showed it — an admin just saw a bare score and a progress bar, with nothing explaining why a pro stayed "New." Fixed: the breakdown now says plainly, right at the top, how many completed Trothen bookings that pro actually has on record, how many more are needed, and — when it's zero — spells out that a profile stat isn't the same thing as a completed Trothen booking. If Joseph's card is still showing "New," this breakdown will say exactly why (most likely: 0 completed Trothen bookings) — the fix is for him to complete real bookings through Trothen, not something more code can shortcut.

## 16. Best practice: removed the ambiguous "5 jobs" wording everywhere a real pro could misread it
Confirmed live on the real Provider Scores page: Joseph Kollie, with his real 315 jobs / 4.9★ visible right on his own card, still shows "New: fewer than 5 jobs, starter allowance" in Admin. Taken at face value next to his own real figures, that reads as a contradiction or a bug — it isn't one (see item 15), but the wording itself was the problem: "5 jobs" never said *which* jobs. Best practice here isn't to fake a score from an unverifiable off-platform claim (that would make the whole Trothen Score meaningless as a trust signal) — it's to say exactly what is and isn't being counted, everywhere this shows up, so nobody has to dig into a breakdown modal to understand it. Every place this wording appears now says "Trothen bookings" / "jobs completed through Trothen," not just "jobs": the admin leaderboard's status badge (now with a tooltip explaining why a high profile figure doesn't count), the "New on Trothen" badge on a pro's public card and profile (both places), and the pro's own "You're new on Trothen" explanation on their own dashboard. No behavior changed — only wording, so nothing needed re-testing beyond confirming the page still renders correctly.

## 17. You can now change the "New on Trothen" rule yourself — no code deploy needed
Straight answer to "are the buttons okay or do we need additional, also change the rule": the three existing buttons (Recompute now, Breakdown, Place on Hold) are each doing a genuinely different job and all three stay — Recompute now re-runs the scoring math, Breakdown explains one pro's number, Place on Hold is a manual account action unrelated to scoring. What was actually missing is what you asked for next: a way to change the rule itself. Until now, "5 completed Trothen bookings before a score stops being provisional" was a fixed number buried in the code — changing it meant a code deploy. It's now a real setting, changeable from Admin → Provider Scores itself.

New panel at the top of Admin → Provider Scores, above the table: it states the rule in plain words, and — for a super admin only — shows the number as an editable field with a Save button. Non-super-admins see the number as read-only text, since this changes how every provider on the entire platform is scored. Saving calls a new super-admin-only endpoint, writes the new number to the same settings store every other platform-wide number already lives in (membership prices, booking response windows, etc.), and logs who changed it and from what to what in the admin access log. The number is restricted to 1–50 — it can never be set to 0, because a score with zero completed Trothen bookings behind it isn't a track record, it's benefit of the doubt, and showing it as a real number would misrepresent what it actually is. Changing the number doesn't retroactively touch anyone's already-stored score — exactly like every other setting on this page, it takes effect the next time scores are computed, so the panel says to click "Recompute now" right after saving if you want it to apply immediately rather than waiting for tonight's automatic run.

Found and fixed one real bug while wiring this up and testing it live end-to-end: my first pass at the admin-facing leaderboard endpoint referenced the signed-in admin the wrong way, which would have made the new "can this admin edit the rule" check always fail and crash that endpoint for every super admin the moment they opened the page. Caught this specifically *because* I ran the whole flow against a live server rather than trusting the code by itself — I started a real local copy, made a real super-admin API call, watched it 500, fixed it, and re-ran the whole thing until a real admin token could view the rule, change it, see the leaderboard reflect the change, and have it take effect on the next recompute, exactly as it will for you.

## 18. "Get the app" in the account menu — fixed a real 3-second dead pause that looked like a broken button
You flagged the account menu (Explore, Settings, Get Help, Terms of Service, Privacy Policy, Get the app, About Us, Sign Out) as "click it and nothing happens." Tested every single item live in a real browser, actually clicking each one and watching what happened on screen — not just reading the code. Seven of the eight open something immediately and did the whole time: Explore, Settings, Get Help, Terms of Service, Privacy Policy, About Us, and Sign Out all worked correctly and instantly in every test. "Get the app" was the real problem, and it's fixed.

Here's what was actually happening: clicking "Get the app" on a computer shows a brief "Opening the installer…" message, then — if Chrome/Edge hands over their own install prompt — opens that. If they don't (which is the common case: that prompt only exists for a few seconds right after the page loads, and by the time you've opened the account menu and clicked this, it has almost always either already been used or already expired), the code was still waiting a full fixed 3 seconds before falling back to showing written install steps — 3 full seconds of a fading toast message and nothing else changing on screen. That's not a broken button, but it reads exactly like one, and three seconds is a long time to stare at nothing.

Fixed: it now only waits for whatever's left of a 3-second window measured from when the *page* loaded, not from the click. A click right after the page loads still gets the full benefit of the doubt (so a real install prompt arriving late isn't missed), but a click any later than that — the realistic case, since it takes several seconds just to open the menu and find the item — goes straight to the written instructions. Verified live: clicking it a few seconds after page load now shows the instructions in under 100ms, down from a flat 3,000ms, with no change to the early-click case.
